# PICO-8 для Karabas Go / Mini / Mini G — план

## Исходные данные (обзор 2026-11-17)

- Готового FPGA-ядра PICO-8 нет нигде (MiSTer, MiST, Analogue Pocket — только просьбы на форумах 2020–21).
  PICO-8 — рантайм Lua, а не процессор: ядро = софт-CPU + Lua VM + API PICO-8 (+ аппаратные помощники).
- Программная основа: **fake-08** (MIT, C++, jtothebell/fake-08 814991a, подмодуль `upstream/fake-08`),
  внутри **z8lua** (форк Lua 5.2, числа 16.16 fixed point, FPU не нужен). Звук из zepto-8.
  Сам PICO-8 проприетарный: только чистая реимплементация, картриджи — от пользователя.
- CPU: VexRiscv (MIT), готовые Verilog-варианты litex-hub/pythondata-cpu-vexriscv
  (Min — без кэша rv32i; Lite — I$ 2K; стандартный — rv32im, I$ 4K + D$ 4K; IMAC — со сжатыми командами). sbt / java не нужны.
- Плата: XC6SLX25, SRAM 4 MB (2M x16, асинхронная), SDRAM 32 MB, RP2040 (занят прошивкой, не хост рантайма).
- Бюджет PICO-8: виртуальный CPU 4–8 MHz (wiki: 2^22 тактов/с), большинство операций Lua ≈ 1 такт;
  т.е. «полная загрузка» ≈ 70–140 тыс. операций VM на кадр 1/60 с.

## Ф0 — замеры (go / no-go), без платы, видео и звука

1. **Нагрузка на хосте** (`src/bench`, fake-08 без экрана): операции Lua VM на кадр, время, доля VM / рисования / звука.
2. **Цена операции в Verilator**: SoC VexRiscv + модель шины с реальным циклом SRAM (16 бит, такты как `archie_sram.v`),
   короткий Lua-бенчмарк, такты на операцию VM: без кэша и с I/D-кэшем в BRAM. Прогоны — секунды.
3. **Площадь и Fmax**: XST + один PAR Mini G (`-t 2`), выводы SRAM в IOB.

Результат Ф0: таблица «кадров/с на картридж на конфигурацию» + строка go / no-go.

(xvst, aaterrain, bench3d_fill не загрузились: многокартриджные / `#include` — не важно для замера.)

Выводы:
- **Звук**: синтезатор fake-08 на float/double стоит больше всей игры (celeste: +134 мкс к 65). На rv32im без FPU это
  программная плавающая точка — **синтезатор только в RTL** (или переписать на fixed point).
- **2D-игры** (celeste, nuke) упираются в рисование: `spr`/`map`/`sspr`/`rectfill`/линии в RTL дают в разы.
- **Тяжёлые 3D-картриджи** (psychik ≈ 3.3 млн ops/с — почти полный бюджет) упираются в саму Lua VM:
  ускорители не помогают, всё решают такты на операцию VM на нашем CPU (Ф0.2).

### Ф0.2 — цена на soft-CPU (2026-11-17)

Инструменты (`src/fw`, `src/sim`):
- `src/fw`: fake-08 + картридж в образе SRAM под rv32im (xPack riscv-none-elf-gcc 15.2.0-1, newlib + libstdc++),
  `make CART=... [FRAMES] [OPS_HOOK=1]`. Тот же ввод, что у хостового бенчмарка; число операций Lua совпадает с хостом кадр в кадр.
- `src/sim/iss`: свой быстрый RV32IM ISS (~35 MIPS), модель кэшей (direct-mapped, строка 32 байта), профиль (`prof.py`),
  дамп на кадре K с заглушкой возобновления (`--dump-at`).
- `src/sim/tb_soc`: Verilator, настоящий VexRiscv на модели SRAM 2M x16 (полслова за обращение; I и D делят шину),
  старт с дампа ISS (`--rv 0x3ff000`) — кадры без 45 млн тактов init. Verilator ~1.3 MHz.

Что пришлось починить в сборке под rv32 (не в upstream, флагами в `src/fw/Makefile`):
1. **`luaV_execute` в z8lua fake-08 собран с `optimize("O0")`** (2022, обход бесконечных циклов у максимума fix32 =
   UB знакового переполнения). Лечение: `-fwrapv` + копия `lvm.c` без атрибута. psychik 15.6 → 5.9 млн инструкций на шаг.
   Тест `test/carts/loop_max_val.p8` завершается.
2. **int32_t = long в newlib** → fix32 переводил индексы в int через double (soft-float). Сделали int32_t = int.
3. **Ошибки / yield Lua через C++ throw** — раскрутка стека каждый кадр (~14 %) и `.eh_frame` без регистрации (abort).
   Теперь `LUA_USE_LONGJMP` (в fake-08 нет catch), `.eh_frame` регистрируется при старте.
4. Остаток: **API fake-08 пишет `int x = lua_tonumber(...)`** — неявный `operator double()`, на rv32 soft-float:
   6–18 % инструкций (столбец soft-fp). Чинится правкой API при портировании.

Калибровка (VexRiscv стандартный: rv32im, I$ 4K, D$ 4K write-through), кадры 100–129 celeste, 100–103 psychik:

| | идеальная память | SRAM rd 1 / wr 3 (как archie) | SRAM rd 2 / wr 2 |
|---|---:|---:|---:|
| celeste CPI | 2.46 | 3.76 | 4.67 |
| psychik CPI | 2.55 | 4.25 | — |

Модель `cycles = 1.85·instr + (I$miss + D$miss)·8·(1+2·rd) + stores·(1+1.7·wr)` сходится со всеми прогонами Verilator
(базовый CPI 1.7–2.0). Нагрузка (ISS, шаги 100–160, I$/D$ 4K):

| celeste | 0.18 млн | 2 199 | ~80 | 8.0k / 2.3k / 0.7k | 2.5k / 1.0k | 15k |
| nuke | 2.7 млн | 7 458 | ~370 (рисование) | 91k / 20k / 5.7k | 14k / 4.1k | 144k |
| thndrbld | 3.0 млн | 27 217 | ~110 | 174k / 36k / 14k | 47k / 11k | 281k |

Выводы Ф0.2:
- Наш soft-CPU в лучшем реальном варианте (кэши 16–32K, 80 MHz, без soft-float) — это примерно **2–4 % бюджета PICO-8**:
  psychik (почти полный бюджет PICO-8) идёт на 8–9 %, thndrbld (~половина) на 15–18 %.
- В реальном времени пойдут только **лёгкие картриджи уровня Celeste** (единицы процентов CPU PICO-8).
  Средние 2D (nuke) — 15–25 %; RTL-ускоритель рисования даст им, грубо, ×2, но не до 100 %.
- Цена одной операции Lua на VexRiscv ≈ 110 инструкций × CPI ~2 ≈ 200+ тактов — это и есть потолок: ускорители
  рисования и звука не трогают VM, а кэш / частота дают ещё ×2–3, нужно ×10–30.
- Предварительный итог: **no-go для «PICO-8 вообще» на софт-CPU**; go только как «плеер лёгких картриджей».
